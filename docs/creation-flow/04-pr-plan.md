# תוכנית פיצול ל־PRים

עקרון: כל PR קטן, ניתן לאימות לבד, משאיר את המערכת במצב עקבי (לא חצי־מיגרציה). מיזוג ל־main רק באישור מפורש שלך.

תלות חיצונית לתכנון:

| פריט | הערה |
|------|------|
| PR מובייל תצוגה מקדימה | קיים כענף/PR נפרד — למזג לפני שינויי עורך מובייל נוספים |
| ענף מסמך זה | `docs/creation-flow-redesign` — מסמכים בלבד |

---

## סדר מומלץ (אסטרטגי)

```
P0  מסמכים (הענף הנוכחי)
P1  ניקוי stubs גלויים + רכיב העלאה משותף (בלי שינוי אשף עדיין)
P2  הסרת שער «החבילה מוכנה» + מגירת כיתוב/האשטאגים בעורך
P3  publishTarget + מיפוי מרכזי + היררכיית CTA הורדה
P4  מסלול מהיר ב־UI (S0–S2) על החוזים מ־P3
P5  Placeholder לחיץ / החלפה מהקנבס
P6  אנליטיקה מלאה + באנר מותג אחרי הורדה
P7  (אופציונלי) יחסי קנבס שונים לפי יעד
P8  (אופציונלי) אחסון תמונות בשרת
```

אסור לקפוץ ל־P4 לפני P1–P3: אחרת נבנה UI על חול (בלי חוזה יעד, בלי העלאה אחידה, עם שער ביניים).

## תלות בין PR קיימים לעבודה החדשה

```
main
 ├─ (קיים) PR מובייל תצוגה/כיוונים ──► למזג לפני P5 מובייל
 └─ docs/creation-flow-redesign (P0)
       └─ אחרי אישור המפרט:
            P1 → P2 → P3 → P4 → P5 → P6 → (P7/P8)
```

כל Pi = ענף אחד לעבודה הזו בלבד. לא לערבב עם תיקוני באגים לא קשורים.

---

## מה לא לעשות בשום PR

1. להוסיף «בקרוב» במסלול הראשי.
2. לבנות אשף שני עם state נפרד.
3. לשנות פרומפטי AI גדולים באותו PR עם שינוי UX זרימה.
4. למזג ל־main בלי אישור מפורש.
5. לפתוח מספר ענפים מקבילים לאותו סוכן לאותה מטרה.
6. להשאיר מסך שער + מגירה «ליתר ביטחון» אחרי P2.
